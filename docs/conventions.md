# Consumer conventions

What a project using `@x-wp/wordpack` must look like on disk, and how the
config fields translate into output paths.

## Minimal project layout

Mirror of `test/`:

```
<project-root>/              ← env.basePath (pass via --env basePath=./)
├── assets/                  ← paths.root.src   (default 'assets')
│   ├── scripts/             ← paths.scripts.src (default 'scripts')
│   │   └── admin/
│   │       └── list-page.ts
│   ├── styles/              ← paths.styles.src (default 'styles')
│   │   └── admin/
│   │       ├── metabox.scss
│   │       ├── list-page.scss
│   │       └── cte.scss
│   ├── images/              ← paths.images.src (default 'images')
│   └── fonts/               ← paths.fonts.src  (default 'fonts')
├── dist/                    ← paths.root.dist (wiped on every build)
│   ├── js/                  ← paths.scripts.dist
│   ├── css/                 ← paths.styles.dist
│   ├── images/
│   ├── fonts/
│   ├── assets.json
│   └── assets.php
├── wpwp.config.ts
└── webpack.config.ts
```

`dist/` is wiped synchronously during `buildConfig` (see
[pipeline.md](./pipeline.md#step-5--synchronous-dist-wipe)); don't store
anything in it that isn't regenerated by webpack.

## The two config files

### `webpack.config.ts`

A one-liner that hands off to the library:

```ts
import buildConfig from '@x-wp/wordpack';

export default async (env: Record<string, string>) => buildConfig(env);
```

The default export is an async function because `buildConfig` does file
I/O and dynamic imports. `webpack-cli` awaits it before starting the
compiler.

### `wpwp.config.ts`

Default-exports a `WordPackConfig`. The test fixture is the simplest
realistic example:

```ts
import { WordPackConfig } from '@x-wp/wordpack';

const config: WordPackConfig = {
  bundles: [
    {
      name: 'admin',
      files: [
        './styles/admin/metabox.scss',
        './styles/admin/list-page.scss',
        './scripts/admin/list-page.ts',
        './styles/admin/cte.scss',
      ],
      splitChunks: true,
      chunkMinSize: 100,
    },
  ],
  paths: {
    scripts: { src: 'scripts', dist: 'js' },
    styles:  { src: 'styles',  dist: 'css' },
  },
  sourceMaps: false,
};

export default config;
```

See [configuration.md](./configuration.md) for every field you can set.

### Discovery order

If `webpack.config.ts` calls `buildConfig(env)` without a second argument,
the library looks for `wpwp.config.ts` under `env.base` (= `basePath`) at
these relative paths, in order:

1. `./`
2. `./assets/`
3. `./assets/wordpack/`
4. `./assets/webpack/`
5. `./assets/build/`

The first one that exists wins. Override by passing an explicit filename:
`buildConfig(env, 'my-custom.config.ts')`.

## How `bundles[].files` resolve

`bundle.files` entries are relative to `cfg.path('src', 'root')` — the
absolute `<basePath>/<paths.root.src>/` — because `SharedConfig` sets that
as the webpack `context`. Webpack treats entry strings as relative-to-
context.

Files are grouped into webpack entries by basename-without-extension
(`BundleConfig.entry` getter, `bundle.config.ts:64-75`). That means:

```ts
files: [
  './styles/admin/metabox.scss',
  './styles/admin/list-page.scss',
  './scripts/admin/list-page.ts',
  './styles/admin/cte.scss',
]
```

produces webpack entries:

```ts
{
  metabox:   ['./styles/admin/metabox.scss'],
  'list-page': ['./styles/admin/list-page.scss', './scripts/admin/list-page.ts'],
  cte:       ['./styles/admin/cte.scss'],
}
```

`metabox.scss` and `list-page.scss` are separate entries because they have
different basenames. `list-page.scss` and `list-page.ts` share a basename,
so they collapse into one `list-page` entry that emits both JS and CSS.

## Output filename templates

Defaults (`WordPackConfig`):

| Template | Default | Emitted as |
|----------|---------|------------|
| `filename` | `'[name].[contenthash:6]'` | `js/<bundle>/<name>.<hash>.js` and `css/<bundle>/<name>.<hash>.css` in production |
| `imagename` | `'[name]'` | `images/<name>.<ext>` |
| `fontname` | `'[name]'` | `fonts/<name>.<ext>` |

Any `[ext]` you add to `filename` / `imagename` / `fontname` is stripped
by `@Transform` before webpack sees it — webpack's `asset/resource` rules
already append the extension. Just leave it off.

In dev mode, `cfg.asset` returns `'[name]'` instead of `filename`, so
JS/CSS come out hashless for faster rebuilds. Production always hashes.

## Output directory layout

With defaults:

```
dist/
├── js/
│   ├── <bundle-name>/<entry>.<hash>.js          ← direct bundle entries
│   └── <vendor>/<vendor>.<hash>.js              ← split chunks
├── css/
│   ├── <bundle-name>/<entry>.<hash>.css         ← direct bundle entries
│   └── vendor/<vendor>.<hash>.css               ← CSS coming from split chunks
├── images/**
├── fonts/**
├── assets.json
└── assets.php
```

The per-bundle subdirectory (`js/admin/...`, `css/admin/...`) comes from
`EntryConfig` (`output.filename`) and `CompileConfig.cssName`. Vendor
chunks end up under a directory named after the npm package, because
`OptimizeConfig.chunkName(module)` derives `<vendor>/<vendor>[-subpackage]`
from `module.identifier()`.

## Asset manifest

Every bundle's emitted assets flow into one shared `assets.json` that looks
like:

```json
{
  "css/admin/cte.css":          "css/admin/cte.abc123.css",
  "css/admin/list-page.css":    "css/admin/list-page.def456.css",
  "css/admin/metabox.css":      "css/admin/metabox.ghi789.css",
  "js/admin/list-page.js":      "js/admin/list-page.jkl012.js",
  "js/classnames/classnames.js":"js/classnames/classnames.mno345.js"
}
```

The key is the stable "logical" name (directory of the emitted file +
original basename). The value is the actual emitted filename, with
contenthash in production. See
[services.md](./services.md#manifestentryformatter) for the exact rewrite
rule.

A twin `assets.php` is written next to the JSON with aligned formatting,
ready to be `require`d from a WordPress plugin/theme:

```php
<?php
return array(
    'css/admin/cte.css'           => 'css/admin/cte.abc123.css',
    'css/admin/list-page.css'     => 'css/admin/list-page.def456.css',
    'js/admin/list-page.js'       => 'js/admin/list-page.jkl012.js',
    // ...
);
```

Typical WordPress consumption:

```php
$assets = require __DIR__ . '/dist/assets.php';
wp_enqueue_script(
  'my-plugin-admin',
  plugins_url( $assets[ 'js/admin/list-page.js' ], __FILE__ ),
  [ 'jquery' ],
  null,
  true,
);
```

## Env flags

Pass via `webpack-cli` `--env` or `--watch`:

| Flag | Effect |
|------|--------|
| `--env basePath=<path>` | Sets the project root (`cwd`-relative is fine). Resolved with `path.posix.resolve` so forward slashes work on Windows too. |
| `--env production` | Switches `cfg.mode` to `'production'`, `devtool` to `false` (regardless of `sourceMaps`), `minimize: true`, enables all minimizers. |
| `--watch` | Sets `WEBPACK_WATCH=true`, which `WordPackEnv.watch` picks up. Disables `splitChunks` (for faster incremental rebuilds) and enables webpack's watcher with `aggregateTimeout: 600`, `poll: 1000`. |

## Bundled WordPress-friendly externals

By default `cfg.externals` maps these to `window` globals (because WordPress
registers them on the front-end):

```ts
{ jquery: 'jQuery', underscore: '_', backbone: 'backbone', lodash: '_' }
```

You can replace or extend this by setting `externals` in your config. When
you do, pair it with `externalsType: 'window'` or set it through the
`override` field to change it — `SharedConfig` hard-codes `externalsType:
'window'` at `shared-config.service.ts:20`.

## Opting out / extending

Every bundle and the global config both carry an `override:
Partial<Configuration>` field. Those are merged last in the pipeline (see
[pipeline.md](./pipeline.md#step-3--per-bundle-merge)), so anything you set
there wins over the library's defaults. Use global `cfg.override` for
changes that apply to every bundle (e.g. adding a `DefinePlugin`), and
`bundle.override` for bundle-specific tweaks (e.g. disabling a loader for
one bundle).

Because `webpack-merge` concatenates arrays, your plugins are *added* to
the stack, not replaced. To replace a loader rule, you'll need to produce
the full `module.rules` in your override and accept that both versions run.
